# 提交前起独立 agent 做 code review

自己写的代码自己看，盲区是同一个。业务仓库的改动在 **commit 之前**，起一个独立子 agent
做 review，它不共享主会话上下文，只看需求描述和 diff 自己判断。

顺序：**改完 → 构建通过 → review → 处理阻塞项 → commit**。

## 什么时候要 review

用户让 commit 业务仓库（公司 GitLab 上的项目）的改动时，默认都要。

可以跳过（跳过时在回复里一句话说明跳过了、为什么）：

- 纯样式数值 / 文案 / 常量调整，且 diff 很小（大致 ≤ 20 行、不涉及逻辑分支）
- 合并到 sit/uat 等部署分支的 merge 提交、cherry-pick：内容在功能分支提交时已经 review 过
- `~/.kiro` 配置仓库的规则文档改动
- 用户明确说「这次不用 review」

一个任务分多段提交（见 `git-workflow.md`「做完一段就提交」）时，**每段各 review 一次**，
只看这一段的 diff，不要把整个任务的累计 diff 重复送审。

## 怎么起

用 `subagent` 工具（blocking 模式，单 stage），`role` 用 `kiro_default`，`model` 指定
`claude-sonnet-5` 省倍率（不必跟主会话一样用 opus）。

prompt 里给这些，**不要把 diff 贴进 prompt**（让 reviewer 自己跑 git，既保持独立，也省主会话上下文）：

- 仓库路径、当前分支
- 送审范围：暂存区就是 `git diff --cached`；已有本地提交未推的就是 `git diff <merge-base>..HEAD`，写明具体命令
- 需求是什么（一两句话 + JIRA 号），reviewer 没有这个上下文就没法判断「做没做对」
- 硬约束：**只读，不改文件、不 git add/commit/stash/checkout**；需要的话可以读改动文件的上下文、跑 lint

让 reviewer 按这几项看：

1. 正确性：逻辑错误、边界条件（空值、空数组、接口失败）、异步时序
2. 需求覆盖：需求里说的点有没有漏
3. 夹带：与需求无关的改动、调试代码（`console.log`、`debugger`、写死的 token/环境地址）
4. 安全：密钥进仓库、`v-html` / `innerHTML` 拼用户输入、URL 参数未校验直接用
5. 一致性：和项目已有写法是否一致（组件、请求封装、i18n 多语言是否每种语言都配了）

输出格式要求它固定成三档，每条带 `文件:行号` 和一句理由：

- **阻塞**：不改会出 bug / 安全问题 / 需求没做到
- **建议**：可读性、写法更好，不改也能上
- **无问题**：直接写「无阻塞项」

## review 结果怎么处理

- **阻塞项**：改掉；改动不止一两行的，修完再送审一次，**最多复审一轮**，还有分歧就列给用户定
- **建议项**：属于本次改动范围内、改了无风险的顺手改；超出范围的不改，列给用户
- reviewer 判断有误（误报）：不改，在回复里说明为什么不采纳
- 回复里用一两句话交代 review 结论（如「review 无阻塞项，2 条建议已采纳 1 条」），不要整段转贴 reviewer 的输出

## 不要做的事

- 不要因为 review 发现的问题顺手扩大改动范围（改别的模块、重构周边代码）
- 不要让 reviewer 直接改代码或提交——修改由主会话做，责任清楚、diff 可控
- reviewer 起不来（工具报错）按 `error-handling.md` 重试一次，仍失败就在主会话自己按上面五项过一遍，
  并在回复里说明「独立 review 没起来，改为自查」
