# 接到需求直接做完，做完再汇报取舍

用户明确提过（2026-10-27）：「接到我的需求直接按照最佳实践做一版出来，尽量不要让我来确认，
可以做完再讲有些疑问的点、取舍的点」。反例：一个改文案的 JIRA，改完还停下来让用户确认一遍再提交，用户不满意。

## 默认做法

- 需求给到就**一路做到底**：读需求 → 改代码 → 构建/lint → 自测 → review → 提交并推功能分支 →
  实测通过的按项目惯例合部署分支（sit 等）→ 查 pipeline 和线上代码。中间不停下来问。
- 需求有歧义：按原型、现有代码、同类页面惯例选最合理的做法，**记下来做完再讲**，
  每条写清楚「怎么选的、为什么、要改的话动哪里」。
- 接口没出：照原型和同类接口结构先写，集中标 TODO，汇报里列清单，不要卡住。
- 汇报里不要再问「要不要提交 / 要不要发 sit」这类下一步，能做的已经做完；只把需要用户或产品拍板的点列出来。
- 简单小改动（文案、样式、常量）同样直接改完、提交、按惯例发出去，再告诉用户改了什么。

## 仍然要先停下来的情况

这些是硬边界，和上面不冲突：

- 需要用户本人操作：CAS / GitLab 登录（agent 触发不了记住密码的下拉框）、OAuth、验证码、真机。
- 生产环境动作、master / main（只能走 MR，见 `git-workflow.md`）、UAT 和生产的后台配置。
- 改多人共用的权限角色、删数据、force push 等不可逆操作。
- 会产生真实业务影响的写操作（真实下单、强平、冻结、撤单等），测试环境也只验证查询和参数构造。
- 环境 / 工具链类阻塞（见 `error-handling.md`）。

## 用户背景：前端转后端，遇到后端概念先用前端的话解释（2026-11-10）

用户是前端开发，第一次写 Java 后端。用户明确要求：**碰到后端/运维/数据库的概念时，先用前端能看懂的语言解释一下**，
再往下做，不要默认他懂。

- 触发时机：第一次在对话里用到某个后端概念（事务、私服/Maven、Bean 与依赖注入、Feign、MQ、分布式锁、
  异步线程池、Mapper/ORM、SNAPSHOT、Apollo/Consul 等）。同一概念解释过一次就不用反复解释，除非用户再问。
- 写法：先给**一句话定义**，再给**前端类比**（npm/package.json、Promise、git、Redux、axios 拦截器、localStorage 等），
  最后落到**这次代码里的具体例子**。类比要说明**哪里不一样**，别让类比误导（例如私服 ≠ node_modules）。
- 篇幅控制：不是写教程。一个概念 3~8 行，够他在评审、和同事沟通时说得清楚。
- 报告里出现不得不用的术语时，括号里加半句人话，例如「事务（一组要么全成功要么全回滚的数据库操作）」。
- 这条是对解释方式的偏好，不改变其他规则：该动手做的照做，解释放在做完的汇报里或做之前的一两句里，不要因为解释而停下来等确认。

已经跟他解释过的概念（不用重复讲，除非他再问）：pom.xml ≈ package.json；私服（Nexus）≈ 公司内部 npm registry；
Feign 是 jar 里的一个接口类（调用其他服务的客户端）；`SNAPSHOT` 表示会变的开发版本；事务（见下次对话的解释）。
