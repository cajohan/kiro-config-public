# 工具报错时的处理策略

工具调用失败**不要直接终止整个任务**，按下面三级降级走，全程不要停下来问，直到三级都走完。

> ⚠️ 两个例外，走三级降级之前先看「立刻停下来问用户」那一节：
> **环境 / 工具链类阻塞** 和 **预计要烧大量 credits 的动作**。

## 一级：原样重试一次

瞬时错误（网络抖动、传输层报错、`Improperly formed request`、超时）大多重试就好。
只重试**一次**，不要连着试三四次刷屏。

## 二级：换一种方法拿同样的信息

一级失败说明不是抖动，是这条路本身有问题。换手段，别在同一个入口上打转。举例：

| 失败的操作 | 换的方法 |
|---|---|
| 读图片失败 | 缩小 / 转 JPEG 再读；仍失败就放弃看图，改用程序读像素、量 DOM 数值 |
| 抓网页失败 | 换 ego-browser 的另一种取法（snapshotText / js / cdp）；或直接读接口 |
| 装依赖失败 | 换包管理器命令、换镜像、或跳过该依赖用替代实现 |
| 命令行工具缺失 | 用 python / node 内联脚本实现同样的事 |

## 三级：跳过，继续往下做

两级都失败就**记下来继续**，不要卡在这一步。要求：

- 在当轮回复里一句话说明「X 没做成，原因是 Y，已跳过」，不要藏起来
- 如果这一步是**验证性**的（截图、看图、跑 lint），跳过后要说明「改用什么方式确认过了」或「这块未经验证」
- 如果这一步是**任务必需**的（拿不到就没法继续写代码），才停下来问用户

## 什么情况下反而应该立刻停

- 涉及破坏性操作的报错（push、删数据、改生产配置）——不要重试，先问
- 报错信息提示权限/认证问题——重试无意义，交给用户处理
- 同一个根因在不同地方反复出现（说明是环境或前提有问题）——停下来说明，别一路绕

### 环境 / 工具链类阻塞：不走三级降级，直接问用户

构建、dev server、原生模块、依赖装不上这类问题，**用户对自己的机器比你清楚**，
一句「用 nvm 切 12」就能省掉你一整轮摸索，而你自己绕路的代价是：改一堆无关文件、
留一堆孤儿进程、烧掉大量 credits（真实案例见 `local-dev-server.md`）。

识别特征（命中任一条就停下来问，最多先做一次一级重试）：

- 报错里出现 **架构 / 运行时 / 原生模块** 字样：`Unsupported architecture (arm64)`、
  `Unsupported runtime (93)`、`node-gyp`、`NODE_MODULE_VERSION mismatch`、`.node` 加载失败
- 构建/启动**整体挂掉**，且失败集中在一类 loader / 一个依赖上（不是自己改的文件报错）
- 缺命令行工具、缺全局依赖、镜像源不通、端口被别人占

问的时候要给出**你的判断和建议方案**，不要只丢一句「跑不起来」：

> node-sass 在当前 Node 16 + arm64 下加载失败，整个 scss 编译阶段全挂（报错都是同一个环境
> 错误，跟本次改动无关）。README 写的是本地用 Node 10 或 12——要我 `nvm use 12` 重试，
> 还是你本地已经有跑着的 dev server 我直接连？

反面做法（都踩过，别重复）：

- 换掉项目的编译器/依赖去绕（dart-sass 顶 node-sass），连带被迫改业务代码
- 改仓库里跟需求无关的文件让工具链高兴
- 反复起后台服务试，一次不成再起一次

## 预计要烧大量 credits 的动作，先说成本再动手

用户的额度是有限的，长任务中途耗尽会直接中断。**开销大的动作先报价、等一句确认**：

- 全量构建 / 全量测试要跑好几分钟，且**要跑多轮**（一次确认性构建不用问，反复试要问）
- 起 dev server + 多轮截图走查（图片进上下文很贵）
- 大范围读取（几十个文件、整个目录树）或大规模改写
- 反复试错型探索：同一件事换三四种方法试

说法要具体，给出预估和更省的替代：

> 要在 6 种语言×端组合下逐屏截图核对，大概十几张图，比较费 credits。
> 要不要缩成「PC 繁中 + H5 繁中」两组，其余我只量 DOM 数值不截图？

另外：**任务做完一段就提交**（见 `git-workflow.md`），这样中途额度耗尽也不会白干。

## 不要做的事

- 同一条命令连续重试三次以上
- 把报错当没发生，继续输出「已完成」
- 因为一个非关键步骤失败就中断整个任务并等用户指示
