# 验证时机约定

## 不要每改一处就跑构建

前端项目本地通常挂着 dev server（`yarn dev` 之类），改完保存就能在页面上看到效果。
样式微调、文案改动这类小改动**改完直接说明改了什么，等用户在页面上确认**，不要每次都跑一遍
生产构建——构建要几十秒到几分钟，一轮 UI 走查下来会重复几十次，纯属浪费。

判断规则：

- 样式、文案、常量值等小改动 → 改完即止，交给用户在本地页面确认。
- **commit 之前跑一遍构建**，确认这一批改动整体能编译通过。
- 改完如果不确定语法是否正确（大段重构、复杂模板改动），可以跑一次确认，但要说明为什么。

## 什么情况下仍然要立刻验证

- 结构性改动：新增/删除组件、改动构建配置、动依赖、改类型定义。
- 报错定位：用户反馈编译失败或运行时报错时。
- 涉及 CI/部署的改动：合并到部署分支前必须构建通过。

## 用户负责的部分

用户本地在跑 dev server 时，页面表现（位置、间距、颜色是否符合设计稿）由用户确认。
不要反复声称"需要你实机确认"，说明改了哪些值即可；除非改动确实存在无法自查的风险
（例如依赖设备 DPR、安全区、字体字形的效果），那种情况明确指出来。

## 自己能确认的，不要甩给用户确认

用户明确提过（2026-10-13）：**我能用工具查到的事实，自己查完再汇报**，不要在结尾列一串
「需要你确认 xxx」。把能查的查掉，只把真正查不了的留给用户。

动手前先问自己：这件事我有没有手段确认？有就直接做：

| 想说「需要你确认」的事 | 自己怎么确认 |
|---|---|
| pipeline 有没有触发 / 成功 | ego 打开 GitLab，在页面里 `page.fetch('/api/v4/projects/<url编码的 group/project>/pipelines?sha=<完整sha>')`，再查 `/pipelines/<id>/jobs` |
| 部署后线上是不是新代码 | curl 部署环境的 `index.html`，拉对应 chunk，grep 本次改动的特征代码（如 `path:"/result"`） |
| 远端分支是否同步、有没有推错 | `git status -sb`、`git branch -r --contains <sha>`、`git diff origin/<分支> --stat` |
| 单子/文档/接口文档内容 | ego 读，见 `web-access.md` |
| 接口返回、字段结构 | ego 在已登录页面里 `page.fetch` 调接口看 |

### 业务流程可以自己端到端走

H5 页面、中台审核这类流程，能用 ego 登录测试环境自己走就自己走，具体环境地址和登录方式见
`internal-project-notes.md`。

真正留给用户的只有这几类：

- 需要真机 / App 环境才能复现的行为（如 webview 内 `window.close()` 是否生效）
- 需要别人提供的信息（测试的操作步骤、产品对行为变化的决策）
- 需要用户本人授权的操作（OAuth device flow、验证码、生产环境动作）

留给用户时说清楚**为什么我确认不了**，而不是默认把验证环节推出去。

### 需要用户动手时，给一条能直接粘贴的命令

用户明确提过（2026-10-19）：**尽量简化留给用户的操作**。能用命令行完成的，就给一条完整、可直接复制粘贴执行的命令，
不要让用户自己打开文件找位置手改（例如 `~/.kiro/agents/`、`~/.kiro/settings/` 有写保护，只能用户改时）。

- 命令要幂等（重复执行不会出错或重复添加），改 JSON 用 `python3 -c` 读写，不要用 sed 拼。
- 给之前先在 `/tmp` 的副本上跑一遍，确认结果正确、只改了该改的部分。
- 只有命令行确实做不到的（浏览器里点授权、输验证码、真机操作）才描述手动步骤。
