# 验证时机约定

## 不要每改一处就跑构建

前端项目本地通常挂着 dev server（`yarn dev` 之类），改完保存就能在页面上看到效果。
样式微调、文案改动这类小改动**改完直接说明改了什么，等用户在页面上确认**，不要每次都跑一遍
生产构建——构建要几十秒到几分钟，一轮 UI 走查下来会重复几十次，纯属浪费。

判断规则：

- 样式、文案、常量值等小改动 → 改完即止，交给用户在本地页面确认。
- **commit 之前跑一遍构建**，确认这一批改动整体能编译通过。
- 改完如果不确定语法是否正确（大段重构、复杂模板改动），可以跑一次确认，但要说明为什么。

## 什么情况下仍然要立刻验证

- 结构性改动：新增/删除组件、改动构建配置、动依赖、改类型定义。
- 报错定位：用户反馈编译失败或运行时报错时。
- 涉及 CI/部署的改动：合并到部署分支前必须构建通过。

## 用户负责的部分

用户本地在跑 dev server 时，页面表现（位置、间距、颜色是否符合设计稿）由用户确认。
不要反复声称"需要你实机确认"，说明改了哪些值即可；除非改动确实存在无法自查的风险
（例如依赖设备 DPR、安全区、字体字形的效果），那种情况明确指出来。

## 自己能确认的，不要甩给用户确认

用户明确提过（2026-10-13）：**我能用工具查到的事实，自己查完再汇报**，不要在结尾列一串
「需要你确认 xxx」。把能查的查掉，只把真正查不了的留给用户。

动手前先问自己：这件事我有没有手段确认？有就直接做：

| 想说「需要你确认」的事 | 自己怎么确认 |
|---|---|
| pipeline 有没有触发 / 成功 | ego 打开 GitLab，在页面里 `page.fetch('/api/v4/projects/<url编码的 group/project>/pipelines?sha=<完整sha>')`，再查 `/pipelines/<id>/jobs` |
| 部署后线上是不是新代码 | curl 部署环境的 `index.html`，拉对应 chunk，grep 本次改动的特征代码（如 `path:"/result"`） |
| 远端分支是否同步、有没有推错 | `git status -sb`、`git branch -r --contains <sha>`、`git diff origin/<分支> --stat` |
| 单子/文档/接口文档内容 | ego 读，见 `web-access.md` |
| 接口返回、字段结构 | ego 在已登录页面里 `page.fetch` 调接口看 |

### 下「没有 / 不支持 / 不存在」这类结论前，先把入口走全

「某个页面没有 X」「某个接口不支持 Y」「某个功能不存在」这类否定结论，要比「有」的证据更充分。
少看一处就会得出错的结论，错的结论又会改坏代码（2026-11-02 踩过：说「融资利息管理没有利率设置 tab」，
据此把 ZTHK-21999 的跳转改去了别的页面。实际是只看了默认打开的「当月」tab 的内容，没看 tab 栏，
「利率设置」tab 在那儿放了好几年。用户在 SIT 截图一眼就指出来了）。

下否定结论前必须做到：

- **页面**：在实际环境把页面上所有 tab、子 tab、下拉、弹窗入口都列出来（读 `.el-tabs__item` 等 DOM 文本，
  或者 snapshot 整页），不能只看默认落点的内容。没把入口列全，不算「查过」。
- **代码**：在部署环境对应的分支上搜（如 `origin/sit-xxx`），同时搜路由、组件和 tab 名，不能只搜一个关键词。
- **接口**：swagger 和实际调用都要有；只看 swagger 没搜到，不算「不存在」。
  另外 knife4j 链接里的 `xxxUsingPOST` 是方法名，不是接口路径（2026-10-31 踩过）。
- 汇报时写明「查了哪些入口 / 分支 / 关键词」。证据只覆盖一部分时，结论写「没找到」，不要写「没有」。
- 改代码绕开一个「不存在」的东西之前（比如改跳转目标、去掉某个按钮），再用另一种方式复核一次。

### 「缺接口 / 等后端」这类结论有时效，汇报前当场复测

用户明确要求（2026-11-05）：**接口问题要有实时性，验一下确认了再报告**。
后端在持续补接口，几天前测出的「不支持」很可能已经过时。2026-11-05 踩过两次：

- 汇报「开户分配按套餐名称查询要等后端加 openPackName」，依据是 10 月底的实测。用户在 SIT 一查就能筛，
  当场复测 不传 17 / `liang测试` 1 / `liang` 2 / 不存在 0，后端早已支持模糊查询。
- 汇报「换汇配置的基点 / 汇差等后端出接口」，其实原型写的是「这两列去掉不展示」，根本不需要接口。

规则：

- 汇报里每一条「缺接口 / 后端不支持 / 等后端」，**当轮先在实际环境复测一次**（ego 在已登录页面里
  `fetch`，用对照组：不传、传真实值、传不存在的值，比较 total），写上复测日期和结果再报。
  复用文档里的旧结论时也一样，文档里的结论不能直接转述。
- 同时回原型核对这个字段 / 列是不是本来就要做的：原型说去掉的，不算缺接口。
- 复测发现已支持：顺手把任务文档里的旧结论改掉，并检查前端是不是本来就在传，不用改代码就说明不用改。

### 能自己做的操作也自己做，不要写成步骤交给用户

用户明确提过（2026-10-23）：**我能用工具做完的事，直接做完，不要写成「你在 GitLab 点 xxx、填 xxx」的步骤让用户执行**，
也不要在做之前请示「要不要我来」。上面那张表只覆盖了「确认」，「执行」同样适用：

| 想交给用户做的事 | 自己怎么做 |
|---|---|
| 在 GitLab 手动 Run Pipeline（选分支、填 `CI_COMMIT_MESSAGE`） | ego 打开项目页，在页面里 `page.fetch` POST `/api/v4/projects/<id>/pipeline`（`{ref, variables:[{key:'CI_COMMIT_MESSAGE', value}]}`），或在页面上点 Run Pipeline；触发参数按 README / 历史提交 / `internal-gitlab-manual-build.md` 确定 |
| 盯 pipeline 跑完、看 job 日志 | `page.fetch` 轮询 `/pipelines/<id>`、`/jobs/<id>/trace`，自己读日志下结论 |
| 跑出了不该跑的 job（比如误触发打包） | `page.fetch` POST `/jobs/<id>/cancel` 立刻取消，再告诉用户 |
| 在测试环境 / 中台点按钮走流程 | ego 自己点（见下一节） |

判断口径：**用户已经同意了做这件事（或这件事是任务的自然下一步），而我有工具能做 → 直接做，做完汇报结果。**
仍然要先问的只有：生产环境动作、master/main 合并、删除/覆盖别人的东西、会对外发通知或花钱的操作、
以及用户明确说过「我自己来」的事。

### 业务流程可以自己端到端走

H5 页面、中台审核这类流程，能用 ego 登录测试环境自己走就自己走，具体环境地址和登录方式见
`internal-project-notes.md`。

真正留给用户的只有这几类：

- 需要真机 / App 环境才能复现的行为（如 webview 内 `window.close()` 是否生效）
- 需要别人提供的信息（测试的操作步骤、产品对行为变化的决策）
- 需要用户本人授权的操作（OAuth device flow、验证码、生产环境动作）

留给用户时说清楚**为什么我确认不了**，而不是默认把验证环节推出去。

### 需要用户动手时，给一条能直接粘贴的命令

用户明确提过（2026-10-19）：**尽量简化留给用户的操作**。能用命令行完成的，就给一条完整、可直接复制粘贴执行的命令，
不要让用户自己打开文件找位置手改（例如 `~/.kiro/agents/`、`~/.kiro/settings/` 有写保护，只能用户改时）。

- 命令要幂等（重复执行不会出错或重复添加），改 JSON 用 python 读写，不要用 sed 拼。
- **命令要短，不要给用户长命令**（用户 2026-11-13 明确要求）：给用户的命令控制在一行、约 80 字符以内。
  长的一行在用户终端里会被折行拆开，粘贴后报语法错误（实际踩过：`python3 -c '...'` 一长串，在 `import` 后面被断开）。
  做法：逻辑写成脚本文件放在 `/tmp/<任务名>/`，再给用户一条短命令，例如 `python3 /tmp/cli-edit/edit.py`、`bash /tmp/cleanup/clean.sh`。
  不要再用 `python3 -c '很长的代码'`、带很多参数的 `tar`/`find` 之类的单行；命令里需要多段，也拆成多条短命令，每条各占一个代码块。
  脚本写到 `/tmp` 后先用副本或 `DRY=1` 之类的方式试跑，确认没问题再给命令；用户执行完提醒删掉脚本目录。
- 给之前先在 `/tmp` 的副本上跑一遍，确认结果正确、只改了该改的部分。
- 只有命令行确实做不到的（浏览器里点授权、输验证码、真机操作）才描述手动步骤。

## 功能改动都要实测，不是只跑单测（用户 2026-11-10 要求）

用户明确说明：**每一次功能改动尽量都要测，除非是很简单的改动**（改文案、改常量、纯样式那类）。
上面「不要每改一处就跑构建」只适用于前端样式/文案微调，**不适用于有逻辑的改动**。

- 有逻辑的改动（新增/修改接口、业务规则、状态联动、并发/事务、对外同步）：
  1. 先写单测覆盖分支（纯逻辑 + mock 外部依赖），单测通过。
  2. 再在**真实环境**（本地连测试环境、或已部署的 SIT）把主流程和这次改动涉及的每个分支实际走一遍，
     并且**查数据确认**（接口返回、数据库字段、下游系统的存储），不能只看接口返回 code=0。
  3. 改动之后又补了逻辑（比如 review 后加了锁、加了分支），**要重新实测**，不要拿改动前的结果当结论。
- 单测过了不等于没问题：mock 测不出事务回滚、锁、下游真实字段、配置差异。汇报时写清楚
  「单测覆盖了什么 / 真实环境验证了什么 / 没验证到什么」，没验证到的不要写成「没问题」。
- 实测会改动共享测试环境数据时：用用户提供的测试账号，测完把状态恢复，留下的痕迹（追加类记录）如实告诉用户，
  不要自己用高权限账号去删。生产环境一律不测。
- 实测会产生副作用的服务（消息消费者、定时任务注册、对外通知）要先关掉或指向空地址，见 `internal-project-notes.md`
  的「后端本地连 SIT 实测」一节。
- 后端起服务验证、收尾（杀进程、删含密码/token 的临时文件）遵守 `local-dev-server.md`、`shell-commands.md`。
