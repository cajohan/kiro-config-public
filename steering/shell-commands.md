# 命令写法：复杂脚本先写成文件再执行，不要塞进 heredoc

## 为什么

Kiro 的权限规则（`~/.kiro/settings/permissions.yaml`：全部允许 + 禁止 `git push*master*`）是**先解析命令、再拿解析结果去匹配规则**。
命令解析不了时，任何已保存的规则都匹配不上，每次都会弹 Allow / Deny 审批框，打断用户。

2026-10-21 踩过：`python3 - <<'EOF' ... EOF` 里塞了一段混着单双引号、`\n`、中文的字符串替换脚本，
弹窗提示 `Kiro could not parse this command, so a saved rule would never match it`。
哪种字符组合会解析失败没法预判，所以**统一不往命令里塞大段脚本**。

## 怎么写

- 超过一两行、或者带引号嵌套 / 多行字符串 / 中文的脚本：先用文件写入工具写到 `/tmp/<任务名>/` 下，再用一条简单命令执行：

```bash
python3 /tmp/<任务名>/patch.py
node /tmp/<任务名>/probe.mjs
```

- ego-browser 同理，脚本写成文件后用 stdin 重定向喂进去（和 heredoc 等价，2026-10-21 实测 `taskSpace` 等 SDK 全局函数都可用）：

```bash
ego-browser nodejs < /tmp/<任务名>/check.mjs
```

- 往 Electron 主进程 inspector 里送表达式的写法（`node /tmp/eav/eav.mjs /tmp/eav/run.js`，表达式本身放在文件里）就是对的，照这个思路来。
- git、ls、curl、sips 这类简单的单行命令照常直接跑，不用为它们写文件。
- 临时脚本目录用完就删，和截图的清理约定一样。

## 临时文件一律放 `/tmp/<任务名>/`，不要放进仓库的 `.git/`

用户确认（2026-10-26）：笔记、计划、review 报告、探测脚本等**所有临时文件**都放 `/tmp/<任务名>/`，
任务全部做完后整个目录删掉。

- 不要为了不污染 `git status` 把临时文件写进 `<仓库>/.git/` 下（如 `.git/kiro-xxx/notes.md`）：
  Kiro 对写 `.git` 目录有内置保护，即使 `permissions.yaml` 是全允许，`fs_write` / `str_replace` 写进去也会弹 Allow
  （2026-10-26 一个 workflow 因此弹了 5 次）。
- 起 workflow 时在 brief 里写明临时文件目录（如 `/tmp/<任务名>/`），并让最后一步清理它，
  步骤之间靠这个目录传递的文件（review.json 之类）也放这里。

## 减少来回：改文件就直接改，别绕脚本

用户 2026-11-14 反馈「改个 md 没道理这么慢」。每个工具调用都要等一轮，来回多就慢，会话越长越明显。

- **改一份已有文件，直接用 `str_replace`**（同一文件多处修改就连续几次 `str_replace`，或一次 `fs_write` 重写），
  不要先 `fs_write` 一个 python 脚本、再 `execute_bash` 去执行、再单独跑一遍 grep 核对。
  只有「批量改几十个文件」「需要正则/循环」这类 `str_replace` 做不了的才写脚本。
- **有依赖的调用不要放进同一批并行**：先 `fs_write` 再 `execute_bash` 读/执行它，两个会同时发出，
  后者经常先跑而找不到文件，白白多一轮（2026-11-14 出现了三次）。需要先写后用，就分两步，
  或者用一条命令里的 heredoc/`tee` 一次写完并执行。
- **核对一次就够**：改完文档用一条命令 `grep -n` 看关键行即可，不要再额外查仓库状态、列分支这类和本次改动无关的东西。
- 构建/起服务这类本来就慢的动作（Maven 1~3 分钟、Spring 服务 20~60 秒），能在一次调用里串起来就串起来，
  不要「编译 → 看结果 → 再起服务 → 再看结果」拆成四五轮。
- 机器内存紧（16GB，Kiro 多个进程合计近 4GB，加上 ego、kiro-cli）时，构建会明显变慢；
  感觉慢先 `vm_stat`、`ps -Ao rss,comm | sort -nr | head` 看一眼，确认是不是内存换出，别当成命令本身的问题反复重试。
- 对话很长时会被系统自动压缩成摘要（会话里会出现一段「对话已被摘要」），上下文有上限，不是越来越慢到不能用。
  「长会话会让单步变慢」我没测过，**不要把它当成慢的原因**；实测过的慢因是机器内存吃紧和多余的来回。
  压缩的代价是摘要会丢细节（具体路径、命令、用户说过的约束），之后需要时要重新查。
  所以一个大任务收尾后开新会话是可选的：好处是背景由用户确认过一段话带过去，比自动摘要可控；不是必须。

## 不要做的事

- 不要为了不弹窗去 `permissions.yaml` 里给 shell `'*'` 放行：它会绕过全部命令解析，
  禁止推 master 的那条规则对解析不了的命令很可能就拦不住了。用户已确认不加（2026-10-21）。
- 弹窗出现时不要点 `Always deny`（见 `git-workflow.md` 末尾「审批弹窗」一节）。
